# 首轮完成后界面卡死问题诊断

## 根因

DeepSeek 流的最后一个 usage chunk 曾携带 `LlmUsage` 数据类。`websocket.send_json()` 无法序列化该对象，任务在正文之后异常退出，因而前端收不到 `answer_end` 后的 `turn_end`，并持续保持 busy 状态。

## 修复

- Provider 在边界处将 usage 转为普通字典；最终 `turn_end.usage` 使用相同结构。
- WebSocket 发送前递归转换 dataclass、Enum、Path 和容器，并用 `json.dumps` 作开发期断言。
- 回合任务捕获异常并尽力发送安全的 `stream_error`；正常、取消和异常各只产生一个终止事件。任务 done callback 会读取异常并清理 active 引用。
- 前端所有终止事件统一经过 `finishTurn`，恢复发送按钮、隐藏停止按钮；`cancel_requested` 会将停止按钮显示为“正在停止…”。
- 静态资源响应使用 `Cache-Control: no-store`，前端会在控制台输出 build ID `6ba7af4`。

## 已执行验证

- Python 3.11（`plc` 环境）：`tests/unit/frontend` 和 `tests/unit/llm/test_deepseek_provider.py`，9 项通过。
- 覆盖 usage JSON 序列化、结构化协议字段、正常流的 `usage -> answer_end -> turn_end` 顺序。
- `compileall` 通过，`git diff --check` 通过。

## 未在本机自动执行的验证

真实 PyWebView、DeepSeek、TIA/MCP 工具需要本机 API 配置和实际 TIA 会话，未在此自动启动，避免创建外部模型请求或操作工程。应在 GUI 中验证两轮连续对话、停止生成、思考/快速模式以及真实 TIA 工具调用；浏览器控制台应显示上述 build ID。
