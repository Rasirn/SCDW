# SCDW 项目分析报告

> 分析日期：2026-07-25  
> 分析范围：仓库源码、配置、RAG 模板、示例数据及 TIA Portal 工程文件。本文基于静态审查与 Python 语法编译；未实际启动 TIA Portal、LLM 服务或前端。

## 1. 项目定位

SCDW 是面向 **TIA Portal V17 / S7-1200 PLC** 的智能编程辅助系统。它把自然语言需求、Excel 工程规格和已有 SimaticML（LAD）模板结合起来，通过 LLM 生成或修改 PLC 程序块，再借助 TIA Portal Openness 导入、编译和保存工程。

当前仓库同时包含两类资产：

- Python 应用：MCP 服务、LLM 对话编排、RAG 模板检索、Excel 解析、Web/桌面界面与 Openness 封装。
- TIA Portal 工程快照：`SCDW_FanControl/`、`SCDW_FanCtrl/`、`SCDW_PlcProject/`、`SCDW_Project/`、`SCDW_风机控制/`、`test429/` 等，均包含 `.ap17` 与索引/数据库文件，可作为工程样例或导出来源。

## 2. 总体架构

```text
用户（CLI / Web / 桌面窗口）
        │
        ▼
DeepSeek 对话编排（core/ + frontend/chat_bridge.py）
        │  OpenAI 兼容工具调用
        ▼
MCP 客户端（mcp_client.py） ── stdio ──► MCP 服务（mcp_server.py）
                                              │
                                              ▼
                                      core/tools.py：18 个 MCP 工具
                                      ├─ RAG/rag_retriever.py：XML 模板检索/保存
                                      ├─ data/xlsx_reader.py：Excel 项目规格解析
                                      └─ openness/：TIA Portal Openness API
                                                       │
                                                       ▼
                                              TIA Portal V17 工程与编译器
```

关键设计是“**模板约束下的 XML 生成**”：先检索真实工程导出的 LAD XML，LLM 以模板为结构基线进行修改，随后导入 TIA Portal 并通过编译错误反馈迭代。这比从零生成 SimaticML 的可控性更高。

## 3. 模块与职责

| 模块 | 主要文件 | 职责 | 观察结论 |
|---|---|---|---|
| 启动与 MCP | `main.py`、`mcp_server.py`、`mcp_client.py` | CLI 启动、FastMCP 暴露、stdio 客户端连接 | MCP 服务是全系统的执行入口；`MCPClient` 的 prompts/resources 接口尚为占位实现。 |
| 对话编排 | `core/chat.py`、`core/cli_chat.py`、`core/deepseek.py` | 消息历史、工具调用循环、DeepSeek 适配 | 支持多轮工具调用；默认温度为 1.0，生成 XML 时波动可能偏大。 |
| 工具层 | `core/tools.py` | 会话状态、MCP 工具注册、流程串联 | 代码集中、功能覆盖面广，但文件体积和职责较重，是后续拆分重点。 |
| Openness | `openness/tia_*.py` | TIA API 加载、项目/硬件/标签/块/编译 | 对 S7-1200 槽位、模块版本探测、编译消息递归提取做了针对性处理。 |
| RAG | `RAG/rag_retriever.py`、`RAG/templates/` | 模板扫描、关键词检索、XML 持久化 | 当前为元数据关键词匹配，不是向量检索；适合小模板库。 |
| Excel | `data/xlsx_reader.py` | 硬件、I/O、DB 和功能描述解析 | 输出结构化 `PLCProjectSpec`，可为工程创建与代码生成提供输入。 |
| 前端 | `frontend/app.py`、`chat_bridge.py`、`main_gui.py`、`static/index.html` | FastAPI + WebSocket 流式聊天；pywebview 桌面壳 | 单进程共享一个聊天实例，以锁保证同一时刻仅处理一条请求。 |

## 4. 核心工作流

### 4.1 自然语言生成 LAD

1. 用户在 CLI 或 Web 界面描述 PLC 功能。
2. LLM 通过 `search_plc_templates` 检索模板；命中后以 `get_plc_template(..., full=True)` 获取完整 XML。
3. LLM 修改或生成 SimaticML，调用 `import_lad_xml`。
4. 导入前，系统保存 XML 至 `RAG/generated/`；导入实现会进行 XML 语法检查，并处理若干已知 FlgNet 问题：重复 `IdentCon`、元件排序、多 `Powerrail`、S7-1500 专用 I/O 指令等。
5. 使用 `compile_check` 获取编译消息；修订后覆盖导入，最终 `compile_and_save` 保存工程。

### 4.2 Excel 驱动的工程创建

1. `read_project_spec_from_xlsx` 解析设备清单、I/O、DB 块与逻辑描述。
2. 创建 TIA 工程、添加 CPU/扩展模块、创建变量表及全局 DB。
3. 先编译 DB 以注册符号，再由 LLM 根据逻辑描述生成 FC/LAD 块。
4. 编译、修复、保存。

该流程已具备“分步骤自动化”的基础；目前并不是一个完全确定性的一键工程生成器，因为 LAD 逻辑生成仍依赖 LLM。

## 5. MCP 工具能力

实际注册 18 个工具（以 `core/tools.py` 为准）：

- 会话：`init_tia_project`、`close_tia_session`
- 硬件：`add_plc_to_project`、`add_hardware_module`
- 软件资产：`create_plc_tag_table`、`create_global_db`、`import_scl_block`
- LAD/XML：`import_lad_xml`、`save_lad_xml`、`import_lad_xml_from_file`、`import_template_block`
- 编译与维护：`compile_and_save`、`compile_check`、`delete_plc_block`
- Excel：`read_project_spec_from_xlsx`
- 模板库：`list_plc_templates`、`search_plc_templates`、`get_plc_template`

现有 `PROJECT.md` 中记录的“17 个工具”和部分旧名称已经落后于当前实现，应以本清单更新。

## 6. 数据与模板资产

- `RAG/templates/application/`：9 个应用级 XML 模板（如风机燃气、烧嘴控制、报警、PID 参数控制等）。
- `RAG/templates/basic/`：7 个基础示例（串联、并联、MOVE、多网络、分叉、数学运算、数组/I/O 标签）。
- `RAG/generated/`：AI 生成的 XML 调试留档；目前已有 1 个生成文件。
- `data/`：PLC Excel 模板与完整样例；解析器支持从同一工作表提取硬件、I/O、DB 和功能文字描述。
- 多个 `.ap17` 工程目录：应明确各自的业务用途、来源及哪一个是当前基线工程，避免模板/工程版本漂移。

## 7. 质量、可运行性与主要风险

### 已验证

- 对 `core`、`openness`、`frontend`、`data`、`RAG` 执行了 `python -m compileall`，Python 语法编译通过。
- 代码结构具备较明确的分层，TIA 具体调用集中在 `openness/`，便于替换或补充适配。

### 未完成运行验证的原因

当前解释器缺少 `openai`、`anthropic`、`mcp`、`fastapi`、`uvicorn`、`python-dotenv`、`pywebview`、`pythonnet/clr` 等依赖；仅检测到 `openpyxl`。此外，TIA Openness 需要本机安装 TIA Portal V17 和正确的 PublicAPI 权限。因此本次不能确认 MCP 服务、GUI、LLM 调用和 TIA 导入的端到端运行结果。

### 高优先级问题

1. **凭据管理风险**：`core/deepseek.py` 含硬编码的 API Key，且 `.env` 已被 Git 跟踪，同时 `.gitignore` 未忽略 `.env`。应立即撤销/轮换已暴露密钥，将代码改为只从环境变量读取，并提交 `.env.example` 而不是 `.env`。
2. **依赖声明不完整**：`pyproject.toml` 缺少源码实际导入的 `openai`、`openpyxl`、`fastmcp`/兼容包以及 pythonnet 相关说明；同时包含 `anthropic`，但默认入口使用 DeepSeek。新环境无法直接按项目配置运行。
3. **文档与实现不一致**：根目录 `README.md` 内容很少；`PROJECT.md` 的工具数量、前端框架描述（Flask）和基础模板数量与实际实现不一致。实际前端为 FastAPI，基础模板为 7 个。
4. **测试覆盖不足**：`tests/` 为空；只有 `RAG/test_lad_import.py` 这种需要真实 TIA 环境的手工验证脚本。没有单元测试覆盖 Excel 解析、RAG 排序、XML 修复或 MCP 工具参数。

### 中优先级问题

1. `core/tools.py` 同时承担 MCP 注册、状态管理、XML 流程、Excel 输出格式化，约 1,300 行，修改风险较高。建议按会话、工程、LAD、RAG/Excel工具拆分。
2. RAG 文档称新增模板可“自动重新扫描”，但 `TemplateLibrary` 是进程内单例，除非显式调用 `reload()` 或重启进程，新增文件不会自动进入已创建的实例。
3. Web 端所有连接共享 `_chat` 与消息历史；虽然请求有互斥锁，但不同用户/浏览器会共享上下文，存在会话串扰。应按 WebSocket 或会话 ID 创建独立聊天历史。
4. `main.py` 使用环境变量 `DEEPEEK_MODEL`（拼写错误），前端做了兼容回退；应统一为 `DEEPSEEK_MODEL` 并保留短期兼容。
5. XML 的正则/字符串修复属于针对已知问题的工程化补偿，建议为每类修复增加真实 XML 样例与回归测试，避免影响合法 XML。

## 8. 建议的迭代顺序

1. **安全与可安装性**：轮换密钥；移除仓库内密钥；补全 `.gitignore`、`.env.example` 与 `pyproject.toml`；提供一条可复现安装命令。
2. **建立无 TIA 环境可执行的测试**：为 Excel、RAG、XML 预处理和工具输入验证添加 `pytest` 单元测试；TIA 端到端测试单独标为集成测试。
3. **校正文档与项目基线**：重写 README 的快速启动；同步 `PROJECT.md`；标明当前推荐的 `.ap17` 工程及模板来源版本。
4. **拆分 `core/tools.py`**：保持 MCP 工具名称不变，逐步抽取 session、project、block、template/excel 服务，降低耦合。
5. **提升生成可靠性**：将模型温度降低并固定 XML 输出约束；把编译错误、成功导入 XML 和人工修订 XML 收集为回归样本；模板数量扩大后再评估向量检索。
6. **前端会话隔离**：把聊天对象与消息历史从全局变量移到连接/会话级状态，并设定历史长度和异常恢复策略。

## 9. 推荐运行前检查清单

- 使用独立虚拟环境，按补全后的依赖清单安装依赖。
- 配置 `DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL`，不在源码或 Git 中保存密钥。
- 确认 Windows 上已安装 TIA Portal V17、PublicAPI 路径正确，并且运行账户具备 Openness 使用权限。
- 先运行纯 Python 单元测试，再启动 `python mcp_server.py` 检查工具清单。
- 使用非生产 TIA 工程验证：创建工程 → 添加 CPU → 导入基础模板 → 编译 → 保存。
- 再进行 Excel 与 LLM 的完整闭环验证，并保留 `RAG/generated/` XML 和 TIA 编译消息作为验收记录。

## 10. 结论

项目的业务链路完整：从需求/Excel 输入，到模板检索、LAD XML 导入、TIA 编译与桌面化交互均已有实现，并已针对 SimaticML 的若干实际导入问题沉淀了经验。当前主要短板不在功能设想，而在安全、环境可复现性、测试和文档一致性。优先完成依赖/密钥治理与测试基线后，再扩展模板库和一键自动化，能够显著降低后续迭代风险。
